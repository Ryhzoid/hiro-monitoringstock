# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
npm run dev          # start Vite dev server on port 8080
npm run build         # production build
npm run build:dev     # development-mode build
npm run lint          # eslint over the whole repo
npm run test          # run vitest once
npm run test:watch    # run vitest in watch mode
```

Run a single test file: `npx vitest run src/test/example.test.ts`
Run tests matching a name: `npx vitest run -t "some test name"`

There is no backend, so there is nothing to migrate/seed/deploy server-side — all commands above are the full dev loop.

## Architecture

This is a Vite + React + TypeScript SPA ("hiro-stock-view") scaffolded via Lovable (see `lovable-tagger` dev-only plugin in `vite.config.ts`), using shadcn/ui components (`src/components/ui/*`, configured in `components.json`) on top of Tailwind.

**It is a frontend-only prototype with no backend.** There is no API layer, no fetch/axios calls, and no persistence — confirmed by the absence of any network calls or env-based config in `src/`. All "data" lives in React state seeded from `src/data/dummyData.ts` and is lost on refresh.

### Auth is fake
`src/contexts/AuthContext.tsx` does not validate credentials. `login(email, role)` in `Login.tsx` accepts any email/password and simply trusts the role the user picks from a dropdown. There is no password check, no token, no backend call. When working on auth-related features, don't assume there is a real credential store to integrate with unless asked to add one.

### Data layer
`src/contexts/DataContext.tsx` holds `products`, `transactions`, and `users` as in-memory state, initialized from `src/data/dummyData.ts`, and exposes CRUD-style setters (`addProduct`, `updateProduct`, `deleteProduct`, `addTransaction`, `addUser`, `updateUser`, `toggleUserStatus`). All pages read/write through `useData()` — there is no other data path.

Key domain model (`src/data/dummyData.ts`):
- `Product` tracks `stokAwal` (opening stock), `totalMasuk` (total in), `totalKeluar` (total out). Current stock is *derived*, not stored: use `getStokAkhir(product)` (= stokAwal + totalMasuk − totalKeluar) and `getStokStatus(stokAkhir)` (`'Aman' | 'Menipis' | 'Habis'`) rather than recomputing this logic ad hoc.
- `Transaction` is either `jenis: 'Masuk'` or `'Keluar'`; `addTransaction` in `DataContext` automatically bumps the related product's `totalMasuk`/`totalKeluar` as a side effect — adding a transaction is the only sanctioned way to change stock.
- IDs are generated by array length (`String(products.length + 1)`, `TRX-0001` style), not UUIDs — deleting items and re-adding can produce duplicate IDs; be aware of this if touching that code.

### Routing and role-based access
`src/App.tsx` defines all routes. Two wrapper components gate access:
- `ProtectedRoute` — redirects to `/` if not authenticated; if `allowedRoles` is set and the user's role isn't included, redirects to `/dashboard`.
- `PublicRoute` — redirects authenticated users away from `/` (the login page).

Route → role mapping currently: `kelola-barang`, `barang-masuk`, `barang-keluar` are `admin`-only; `riwayat-transaksi`, `kelola-pengguna` are `manajer`-only; `dashboard`, `stok-barang`, `export-laporan` are shared. The sidebar in `src/components/layout/DashboardLayout.tsx` (`menuItems`) filters visible nav links by the same role logic — **when adding a new route, update both `App.tsx` (route + `allowedRoles`) and `menuItems` in `DashboardLayout.tsx` (nav entry + `roles`)**, since they are two independently-maintained lists that must stay in sync.

### UI conventions
- Path alias `@/*` maps to `src/*` (set in `vite.config.ts`, `vitest.config.ts`, and both tsconfig files — keep them in sync if it ever changes).
- Domain-facing strings (page labels, form text, toasts) are in Indonesian, matching the business domain (PT. Hiro Takashi Mura warehouse system); keep new UI text consistent with this rather than switching to English.
- Toasts go through `useToast`/`toast` from `@/hooks/use-toast` (shadcn toaster) — this is the established pattern for user feedback on form submit/validation, not inline error text.
- TypeScript strictness is intentionally relaxed repo-wide (`strict: false`, `noImplicitAny: false`, `noUnusedLocals/Parameters: false` in `tsconfig.app.json`) and ESLint disables `@typescript-eslint/no-unused-vars` — don't introduce stricter local overrides unless asked.
